## Anomalies

### A1 — `pace` applied differs from `pace` requested (explained, not a bug)

Observed b1 at 0.75 with 0.93 requested. Cause:
`core/client/race/driver-providers.js:165-167` — `damagePct > 20` puts the
driver in `preserve` mode and caps pace at 0.75. Also `attack` mode adds
+0.035 (`:158`), which is why some samples read *above* the requested value.

Gap, not a defect: `bot-watch.mjs` prints the effective pace but not
`targets.mode`, so the strategist cannot see *why* the pace moved.
Proposal: surface `mode` in the bot-watch line.

### A2 — bots pitted without being asked, with `autoPit:false` — NEEDS VERIFICATION

Race 2, lap 2: b3 appeared on hard with 6% wear and b4 showed
`pit: entering`. Neither had ever received `pit:true` from the agent, and
both had `autoPit:false` applied (confirmed in the fleet log at 22:15:40).

The auto-pit branch is correctly gated
(`driver-providers.js:171`, `if (targets.autoPit && ...)`), and
`pitState = "entering"` is only reachable through `startPitStop()`
(`core/client/race/race-systems.js:77-89`), which runs off `pitRequested`.
Who raised `pitRequested` is unknown. Candidates not yet checked: the room
carrying a stop over from the previous race, or `pitRequested` surviving the
rematch page navigation.

### A3 — `state.json` freezes when the bot returns to the room — CONFIRMED

`core/tools/room-bot.mjs:213-227` writes the state file only inside the
`race.html` / `window._DRIVER_` branch. Back on `room.html` the file is
neither updated nor cleared, so it keeps the last mid-race snapshot forever.

Consequences seen: `bot-fleet.mjs:71-76` printed `racing | ... P2 ...` for
five minutes after race 1 had ended, and `bot-watch.mjs` reported a finished
race as still running at lap 3/5. The end-of-race classification for race 1
was lost this way.

Proposal: write a `{phase:"room"}` state in the room branch too.

### A4 — re-arming `pit` caused a double stop (agent error, but an API gap)

On lap 2 of race 2, b1 and b2 were at 98% wear and still showed `pit: none`,
so the agent rewrote `strategy.json` with `pit:true` a second time. The
first call had in fact stayed armed (`race-systems.js:85` returns without
clearing `pitRequested` until the car reaches the pit entry), so both bots
stopped twice and dropped to P6 and P5.

The strategist has no way to see that a box call is armed but not yet
triggered: `state.json` exposes `pit.state` (`none` until the entry) but not
`pit.requested`. Proposal: expose `pit.requested` in the state, so a pending
call is distinguishable from a lost one.

### A5 — 30 s Playwright stall on the room join input

Fleet log, 22:20:25: `[claude-b2] loop page.fill: Timeout 30000ms exceeded`
waiting for `#room-code-input` to be visible. `room-bot.mjs:180-187` checks
`entryVisible` and then fills; the entry can hide in between, and the fill
then blocks the bot's whole loop for 30 s. Proposal: short timeout on that
fill, or re-check visibility immediately before it.
